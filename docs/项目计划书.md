# AI 工具情报与实践助手：项目计划书

日期：2026-10-23

当前独立项目目录：`D:/notebooks/info-agent`。

状态：需求与实施规划，尚未开始本方向的代码开发。

本计划替代《项目计划书-学习与求职版.md》中的销售分析主线。原文档和样例数据保留作历史材料。

## 1. 项目定位

帮助正在学习和实践 AI 工具的人，从关注的信息源中发现值得阅读、验证和动手尝试的内容，生成带来源的个人简报，并把实际试用经验整理成可复用指南。

第一位用户是项目作者本人。初始关注主题：AI 辅助编程工具、工作流自动化、Agent 开发学习资料和可动手实践的开源项目。

目标岗位依据为用户提供的“AI工具应用实习生-北京-2027Campus-秋招”职位描述。本项目重点展示：AI 工具实操、基础代码与自动化、工具测评、操作指南与 Prompt 模板沉淀。

## 2. 要解决的问题

- 信息分散在多个账号和平台，逐个阅读耗时。
- 多条内容讨论同一更新，重复阅读却没有获得更多信息。
- 热门内容不一定适合当前学习阶段，缺少个人相关性判断。
- 看过的信息容易遗忘，收藏后缺少明确的尝试步骤。
- 工具试用过程没有记录，难以复用或向别人说明。

项目的价值以个人实际使用结果判断。抓取量、模型调用次数和框架数量不作为价值指标。

## 3. 完整使用流程

1. 获取或导入近期信息，保留作者、时间、原文链接和内容。
2. 清理格式，识别已处理条目，合并讨论同一事件的内容。
3. 根据用户兴趣和当前学习阶段筛选、排序。
4. 生成简报，分别说明发生了什么、为什么值得关注、建议下一步做什么。
5. 用户针对条目追问，助手依据已有内容回答，资料不足时明确说明。
6. 用户选中一项进行真实试用，保存操作过程、结果和问题。
7. 助手根据真实记录辅助生成测评和操作指南，由用户复核。

“信息简报”与“实测报告”使用不同标记。未亲自测试的内容只能作为待验证信息或试用建议。

## 4. 第一版范围

### 必须具备

- 手动导入一批整理好的信息，先验证处理效果。
- 支持一个明确的个人兴趣配置，可由用户查看和修改。
- 完全重复条目的识别，以及对疑似同一事件的分组。
- 每日简报：默认最多推荐 5 条，有价值的内容不足时允许少于 5 条。
- 每条简报带来源链接、推荐理由及内容完整性说明。
- 对本批信息进行多轮追问，记住当前讨论的条目。
- 记录“有用／无用／准备试用”反馈和已处理状态。
- 将简报保存为 Markdown，便于阅读和归档。

### 第一版完成后再接入

- 一种自动获取方式：优先验证 RSS 或现成数据获取工具。
- 读取原文、补充查询和更深入的核实。
- 定时运行、故障通知、更多平台和更多账号。
- 根据反馈自动调整推荐，而不是一开始设计复杂偏好学习系统。

### 暂不纳入

- 自动读取 B 站和 X 全部关注列表。
- 视频完整内容总结、语音转录和大规模历史回溯。
- 多 Agent、向量数据库、复杂网页界面。
- 自动发布内容或代替用户实际操作并测试陌生软件。

最终希望服务 B 站／X 关注动态，但接入方式与覆盖范围需实测。当前不将任何第三方项目的功能介绍当作已验证的可用接口。

## 5. 输入与输出约定

### 单条输入

保留唯一编号、平台、作者、标题、发布时间、原文链接、内容、采集时间和内容类型。内容类型区分正文、摘录、上游生成的摘要。

发布时间缺失时标记未知，不能用采集时间冒充发布时间。来源链接缺失的条目不进入正式推荐，保留为待补信息。

若输入已经是汇总简报，应尽量保留逐条来源。Agent 根据摘要回答时必须说明依据范围，不能暗示已读过原文或看过视频。

### 单条输出

- 发生了什么：可由来源支持的简洁说明。
- 为什么值得关注：与用户兴趣、学习阶段或当前任务的关联。
- 建议动作：阅读、收藏、动手验证或暂时略过。
- 来源：一条或多条原文链接。
- 依据范围：全文、摘录或摘要；事实与作者观点分别表述。

简报区分“来源明确陈述的内容”和“助手的建议”。不根据标题臆测价格、功能可用性、性能或岗位要求。

### 推荐依据

优先考虑主题相关、内容具体、有可执行步骤、有原始来源的信息。热度不作为主要依据。允许推荐失败记录和局限分析。

同一事件的不同来源可以合并，但不同观点或矛盾描述不能直接抹掉。缺乏依据时提示需要核实。

## 6. 技术与学习安排

继续使用已有 Python、模型配置和文件工具。LangGraph 用来组织清晰的状态和处理分支，不要求每个步骤都由模型完成。

- 普通代码负责：输入校验、编号、链接去重、保存文件、记录处理状态。
- 模型负责：语义相关性判断、事件分组建议、摘要和推荐理由。
- LangGraph 负责：节点间状态传递、失败分支，以及简报后的追问上下文。

第一版以固定流程为主。接入原文读取后，再让助手判断何时需要调用工具补充信息。是否增加规划外循环，以实际任务需要为准。

兴趣配置与历史反馈先用简单本地文件或 SQLite 保存；具体实现放在开发阶段选择。

## 7. 分阶段实施

### 阶段 A：确认一份简报是否有用

- 用户提供或整理 15–30 条真实信息，可来自手动复制或现成工具导出。
- 人工先标出哪些值得看，并给出理由，作为对照。
- 设计一份简报样稿，检查推荐数量、信息密度、来源和建议是否合适。
- 明确一次处理所需的输入字段。

验收：用户能指出推荐里哪些有用、哪些不应出现；这些判断能转化成筛选规则。此阶段可以完全不写代码。

### 阶段 B：实现可重复运行的信息处理流程

- 读取固定格式的样例信息。
- 接入去重、筛选、简报生成与 Markdown 保存。
- 保存本次处理状态，重复运行不重复累计条目。
- 处理输入缺字段、模型输出无效和模型请求失败。

验收：同一批输入可反复运行；所有推荐链接均来自输入；没有合适内容时明确返回无推荐；失败不会生成伪装正常的简报。

### 阶段 C：支持追问与反馈

- 用户可引用某条简报继续提问。
- 记录有用、无用、准备试用，并支持手动修正兴趣配置。
- 追问涉及未知事实时明确说明需要原文或额外信息。

验收：正确识别“第二条”“刚才的项目”等指代；其他会话信息不会串入；反馈可以查阅，不能只显示成功却未保存。

### 阶段 D：验证并接入一种自动信息来源

- 选少量账号或订阅源，验证能否持续获取内容。
- 确认来源覆盖、时间范围、登录要求、更新延迟和可能的费用。
- 对采集失败、部分成功和没有更新分别处理。
- 验证成功后，才考虑定时任务与扩大账号数量。

验收：能够说明本次成功获取了哪些源、哪些失败；不能把采集失败描述成“今天没有值得关注的信息”。

### 阶段 E：真实使用与作品整理

- 连续使用至少 7 天，记录推荐和遗漏情况。
- 从推荐中选择一项，完成真实工具试用。
- 整理 README、简短演示、操作指南、Prompt 模板和项目复盘。

验收：别人能够根据指南运行样例；能展示一次完整流程和一次失败处理；测评结论对应实际记录。

## 8. 验证方式

确定性测试覆盖：字段校验、精确去重、来源对应、重复导入、文件保存和会话隔离。使用假模型检查流程，不依赖真实 API Key。

模型效果由一批人工标注内容评估：

- 推荐有用比例：用户认为有用的推荐数／总推荐数。
- 重要信息覆盖：人工标记值得关注且被推荐的条目数／人工标记总数。
- 重复推荐：同一事件被重复占用推荐名额的情况。
- 来源与事实问题：链接错误、摘要新增原文没有的事实、误把观点当事实。
- 成本与耗时：实际模型调用量、可获取的 token 用量、完整运行耗时。

开发用样例与最终展示用样例分开，避免只对一批内容调提示词。初期报告真实结果，不提前承诺成功率。

如要声称节省时间，用相近规模、相近难度的信息批次比较手工整理与使用助手的耗时，同时记录结果质量差异。
